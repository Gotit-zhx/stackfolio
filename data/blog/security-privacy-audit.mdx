## 为什么要做一次完整审计

个人网站通常同时承担作品集、博客和项目演示三种职责。它既有公开页面，也有后台、数据库、媒体文件和部署配置。只检查首页能否打开，无法说明隐私边界、依赖版本、管理入口和服务器端口是否安全。

这次审计从一个具体问题开始：公开网站和代码仓库中不应该出现不必要的个人身份信息。随后把检查范围扩展到网站源码、生成内容、Git 历史、公开仓库、项目演示、SSH、UFW、Caddy、Docker 和依赖漏洞，最后用真实公网请求验收结果。

## 先收紧公开身份

公开身份统一使用 GitHub 网名 `Gotit-zhx`。网站正文、作者资料、SEO 元数据、搜索索引、RSS、项目说明和 README 都按同一身份检查。简历中的手机号、住址和其他非必要信息没有复制到公开仓库。

这一步还包括 Git 历史。只修改当前文件并不能保证旧提交中的内容已经消失，因为公开分支、标签和 Dependabot 分支都可能继续保留旧版本。确认影响范围后，先保存原始 refs 镜像，再重写公开分支和标签，最后重新扫描远端镜像。历史重写会改变提交 SHA，已有克隆需要重新克隆或重置，所以备份和变更记录必须先完成。

代码搜索和 Git 历史扫描都应作为验收项。当前版本搜索不到敏感身份信息，只能说明当前内容干净；只有对所有可达 refs 扫描，才能确认公开历史也完成处理。

## 网站层的防护

网站层的第一项工作是收紧响应头。生产环境启用 HSTS、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、严格的 Referrer Policy 和 Permissions Policy，并在 Caddy 中隐藏不必要的服务标识。

内容安全策略（CSP）需要和实际页面依赖一起调整。生产配置移除了 `unsafe-eval`，限制脚本、连接、图片、媒体、字体、框架和表单目标的来源。CSP 不是一行配置就能完成的工作：每次新增第三方图片、统计脚本或嵌入内容，都要重新检查来源范围。

博客和 RSS 还要检查环境变量。开发机地址一旦进入搜索索引、站点地图或 Feed，访客就会拿到不可用的链接，也可能暴露内部结构。构建后应搜索 `localhost`、回环地址和测试域名，并用正式域名重新生成公开内容。

## 把管理入口留在边界内

服务器上的公开入口只保留 Caddy 的 80/443 和 SSH 管理端口。主站、PostMaker、百草园、管理台、Redis、数据库和 Docker socket 都绑定到回环地址或内部网络，不直接接受公网请求。

管理台通过 SSH 隧道访问，Docker socket 只以只读方式挂载给需要读取状态的管理服务。这个边界很容易被一次端口映射破坏，因此每次发布后都要重新查看监听端口，而不是只看 Compose 文件。

SSH 侧关闭 root 登录和密码登录，只允许密钥认证；UFW 采用默认拒绝入站策略，只开放实际需要的端口。安全组和主机防火墙要一起检查：云端放行而主机拒绝会导致误判，主机放行而云端暴露范围过宽也会扩大攻击面。

## 演示项目要按真实风险处理

百草园页面公开展示了游客演示账号，这是产品层面明确选择的便利入口，但它不是私密凭据。共享账号只能使用演示数据、最小权限和独立密码，不能复用到个人账号、服务器或第三方服务。账号登录、读取资料、退出和退出后的未授权请求都需要实测。

PostMaker 的采集链路还要关注 SSRF。采集目标应限制为 HTTP/HTTPS 和标准 Web 端口，并拒绝回环地址、内网地址、链路本地地址和保留地址；如果发生重定向，每一跳都需要重新校验。只检查初始 URL 不够，因为攻击者可以把安全的初始地址重定向到内部服务。

上传接口、图片处理、权限检查、请求限制和 Cookie 属性也要一起看。安全检查的目标不是让演示项目看起来像生产平台，而是确保访客不能借演示入口访问服务器内部资源或其他用户数据。

## 依赖补丁要进入发布流程

本次审计发现主站依赖版本已经落后于多个安全修复。补丁发布将 Next.js、`@next/bundle-analyzer`、`eslint-config-next`、sharp、PostCSS、esbuild 和 image-size 更新到安全版本，并用 Yarn resolutions 统一关键传递依赖，避免同一构建中继续安装已知易受攻击版本。

依赖升级不能只看安装命令是否成功。需要同时完成类型检查、Lint、管理台测试、内容与 RSS 测试、生产构建、容器冒烟测试和生产依赖审计。本次 Yarn 生产环境审计返回 `No audit suggestions`；全量开发依赖审计仍可能报告构建、Lint 或文档工具链的上游 advisory，这些依赖不会进入运行时镜像，但应继续跟踪升级。GitHub Dependabot 的依赖图也可能存在刷新延迟，因此远端锁文件、实际构建版本和本机审计结果要分别记录，不能把一个页面状态当成唯一证据。

## 低配服务器上的安全发布

服务器资源有限时，安全发布还要考虑资源峰值。镜像在 Mac 上构建为 `linux/amd64`，服务器只负责加载镜像和替换单个主站容器，不在服务器执行 Next.js 构建，也不同时重启演示项目和数据库。

每次发布前保留旧镜像作为回滚点。发布后先检查容器健康，再从服务器侧请求四个 HTTPS 入口、项目详情页、Feed 和健康接口。服务器侧验收可以避开本地网络代理、DNS 或 TLS 路径差异。

这次发布只替换主站容器，PostMaker、百草园、管理台、Redis、RSSHub 和 DataRadar 保持健康。主站新版镜像健康运行，旧镜像仍可用于快速回退；回退应用镜像不能代替数据库和媒体卷备份。

## 用 Gitflow 固化检查顺序

安全工作也需要可追踪的发布边界。当前流程保持 `feature/* → develop → release/* → main`：先在功能分支完成修复和测试，再用 release 分支做版本验收，最后合并到生产分支并创建标签。

一个可复用的检查顺序是：

1. 扫描公开页面、源码、生成索引、RSS 和 Git 历史。
2. 检查依赖、密钥、环境变量和构建产物。
3. 检查 SSH、UFW、安全组、Caddy、监听端口和容器权限。
4. 在开发机完成跨架构构建和自动化测试。
5. 只发布需要变更的服务，保留回滚镜像。
6. 从服务器侧验收公网入口，并记录资源余量和容器状态。

这样做的好处是每个结论都有证据：源码扫描证明当前文件状态，Git 镜像扫描证明公开历史状态，容器和 HTTPS 验收证明实际运行状态，回滚标签证明出现问题时有可操作的恢复路径。

## 还需要持续做什么

一次审计不能替代长期维护。后续应定期更新依赖、验证数据库和媒体备份恢复、检查公开资料是否发生变化，并重新确认公网监听端口和防火墙规则。公开演示账号需要轮换和监控，个人邮箱也要准备好垃圾邮件和异常登录的处理方式。

安全工作的终点不是把所有风险写成一张清单，而是让每次变更都经过同样的边界检查、测试、发布和回滚流程。对个人网站来说，这套流程比一次性的“上线前检查”更重要。
