## 从准备清单走到公网访问

个人网站的公网发布不只是把域名指向一台服务器。域名解析、ICP备案、HTTPS 入口、应用代理配置和演示服务的实际状态需要分别确认。本次发布将 `gotit-zhx.top` 主站与两个项目演示接入 HTTPS；备案号暂不展示在页脚。

域名入口分别是 `gotit-zhx.top` 与 `www.gotit-zhx.top`、`postmaker.gotit-zhx.top` 和 `baicaoyuan.gotit-zhx.top`。阿里云 DNS 将这些主机名指向服务器公网 IPv4，私有地址不写入公开解析。公网 Caddy 接收 80/443，再按域名转发到服务器回环端口。

## 代理入口与应用端口分开

主站和演示应用仍只监听服务器本机端口，公网请求统一经过 Caddy。管理台、Redis、数据库和 Docker socket 不加入公网代理；管理台继续通过 SSH 隧道访问。这个边界减少了需要直接暴露的服务，也让证书和域名路由集中在一个入口维护。

启用 HTTPS 时，应用配置也要同步调整。主站项目详情中的演示 URL 会在构建时进入页面，因此需要使用真实 HTTPS 地址重建镜像。PostMaker 要使用安全 Cookie；百草园需要匹配正式域名并正确识别代理传递的原始 HTTPS 协议。

## 把构建留在开发机

服务器只有约 1.6 GiB 内存，运行多个应用时余量有限。为了避免在服务器上产生镜像构建峰值，本次在 Mac 上构建 `linux/amd64` 主站镜像，传到服务器后加载并替换主站容器。发布过程按应用逐项检查，不同时进行多项构建或重启；如果资源紧张，应先停止演示服务并观察主站。

上线前保留了原有 Caddy 配置、应用环境文件和旧主站镜像，便于出现故障时恢复入口配置或主站版本。回退应用镜像不能代替数据库备份，数据和应用代码需要分别考虑。

## 演示入口应说明真实体验

公网可访问不代表访客拥有账号，也不代表所有功能都已启用。PostMaker 当前打开登录页，需要有效工作区账号；AI 生成和摘要还依赖模型服务配置。百草园可以打开发现页，注册保持关闭，登录后的写入功能以实际部署配置为准。

项目详情只展示经过核实的 HTTPS 演示地址，并提醒访客不要提交敏感信息。演示环境使用独立数据，不应承诺持续可用、生产级推荐效果或未经验证的性能结果。

## 验收与发布管理

浏览器检查了主站项目页、博客列表和两个演示入口：主站页面及项目详情能打开，PostMaker 显示登录页，百草园显示发现界面。四个主机名的 TLS 入口均已配置。发布后的资源状态还需要持续观察，单次页面加载或健康检查不等于压力测试或备份恢复演练。

本次变更在 `release/v0.1.0` 验收。最终的 Gitflow 步骤仍需在验收和提交后完成：将发布分支合并到 `main` 与 `develop`，创建版本标签并推送。服务器部署应对应明确的代码版本，不能仅凭分支名称推断线上镜像内容。

这次上线留下的检查顺序是：先确认备案、DNS 与安全组，再验证 Caddy 和证书；随后确认各应用的 HTTPS、Cookie、Host 和代理协议设置；最后检查演示入口、后台隔离、容器健康与资源余量。备案号页脚按站点所有者要求暂不添加。
