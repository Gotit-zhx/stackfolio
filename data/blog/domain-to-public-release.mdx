## 从“有域名”到“网站可访问”还差几步

今天为个人网站确定了域名 `gotit-zhx.top`。域名可用并不意味着网站已经上线：域名注册、DNS 解析、ICP备案、HTTPS 和应用部署是不同环节，各自解决不同问题。

- **域名注册和实名认证**确认域名的持有人信息。
- **DNS 解析**把域名或子域名指向服务器的公网 IP。
- **ICP备案**是面向中国大陆提供网站服务前需要完成的合规流程。
- **HTTPS**为浏览器与网站之间的连接提供加密，并让应用能使用安全 Cookie 等配置。
- **反向代理**接收域名上的 HTTP(S) 请求，再把流量转发到服务器本机的应用端口。

把这些环节分开检查，可以避免把“DNS 已经能查到记录”误认为“网站已经可以正式公开”。

## 先确定域名结构和服务边界

当前规划使用同一个根域名：

| 用途     | 域名                                   | 服务器应用                  |
| -------- | -------------------------------------- | --------------------------- |
| 个人网站 | `gotit-zhx.top` 和 `www.gotit-zhx.top` | Stackfolio                  |
| 项目演示 | `postmaker.gotit-zhx.top`              | PostMaker                   |
| 项目演示 | `baicaoyuan.gotit-zhx.top`             | 百草园                      |
| 个人运维 | 不配置公网域名                         | 管理台，仅通过 SSH 隧道访问 |

公网 DNS 只应指向公网 IPv4，不能把服务器私有地址写入公开记录。管理台能够读取主机和 Docker 资源指标，因此继续绑定回环地址，不放进公网反向代理，也不开放对应安全组端口。

域名解析只是把访客带到服务器；它本身不会替应用完成 HTTPS、身份认证或安全隔离。

## 备案与 DNS 按顺序推进

服务对象主要在中国大陆，因此正式开放网站前，需要在云服务商备案控制台确认域名实名主体、备案主体、服务器备案资格和属地材料要求。个人作品集、博客与项目演示的实际内容也应如实填写；若项目包含注册、评论、发帖或用户上传等功能，应先确认对应服务范围和要求。

在备案和发布条件确认之前，网站继续通过 SSH 隧道受限访问。即使 DNS 记录可以提前配置，也不应因此把未完成备案验收的网站作为公开服务开放。

备案通过并决定发布后，再为根域名和各子域名添加 A 或 CNAME 记录，并从外部 DNS 查询核实结果。这样可以把备案、解析和切换公网入口变成可单独验收的步骤。

## HTTPS 代理要和应用配置一起改

计划由公网 Caddy 接收 `80/443`，然后按主机名将请求转发到服务器回环端口：

- 主站转发到 `127.0.0.1:3000`。
- PostMaker 转发到 `127.0.0.1:18787`。
- 百草园转发到 `127.0.0.1:18088`。
- 管理台继续留在 `127.0.0.1:9090`，只走 SSH 隧道。

启用 HTTPS 不只是添加证书。主站中的演示地址会在构建时写入，因此更换域名后需要在本机按 `linux/amd64` 重新构建主站镜像，再传到低配服务器加载。服务器不承担应用镜像构建。

应用侧也要同步检查安全 Cookie、允许的 Host 和 Origin、CSRF 来源，以及反向代理传递的协议头。若代理告诉应用“原始请求使用 HTTPS”，而应用没有正确识别代理，就可能出现 Cookie、重定向或跨站请求问题。

## 低配服务器要求部署顺序可控

目前服务器资源有限，运行 Stackfolio 和两个演示项目时需要继续观察内存与容器状态。部署策略是：

1. 在 Mac 上准备目标架构镜像。
2. 通过 SSH 传输镜像。
3. 服务器只加载镜像和配置，不进行镜像构建。
4. 按应用逐项启动，每项通过健康检查后再继续。
5. 观察可用内存、磁盘、容器重启和日志；资源异常时优先停止演示服务。

这让构建负载留在开发机器上，但也意味着正式发布前要清楚记录代码提交和镜像版本。低负载时的一次健康检查不能代替压力测试或数据恢复演练。

## Gitflow 让“准备”和“发布”分开

公网准备工作放在 `feature/public-release` 分支，包括 Caddy 域名路由模板、HTTPS 环境变量模板和发布清单。功能完成后合入 `develop`；通过真实域名和备案验收之前，不更新生产分支 `main`，也不把项目演示状态改成 `live`。

这个流程让配置可以先被审查和测试，同时不改变当前 SSH 隧道下的受限部署。真正发布时，再从集成版本创建 `release/*`，验收域名、HTTPS、应用行为、资源和备份后合入 `main` 并创建版本标签。

## 今天形成的上线检查顺序

1. 确认域名注册商、实名认证状态和 DNS 托管位置。
2. 在云服务商控制台确认实例具备备案资格，并准备本人备案材料。
3. 完成 ICP 备案；期间维持受限访问。
4. 备案通过后配置 DNS，并从外部网络核实解析。
5. 启用 Caddy 的 HTTPS 入口，管理台仍只允许 SSH 隧道访问。
6. 按 HTTPS 域名重建主站镜像，逐项验证 Cookie、CSRF、代理头和健康检查。
7. 检查备份、恢复流程和低配服务器资源余量。
8. 通过发布分支和版本标签完成上线，验收后再将项目演示标记为在线。

目前已完成的是域名规划、发布配置模板和检查清单；域名解析、ICP备案和公网 HTTPS 尚未完成。因此现有服务仍是受限验收环境，而不是正式公网网站。
